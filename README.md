# VHF Digital Display

A purpose-built, unattended digital display for Veterans Healing Farm (VHF), shown on the Fire TV
television in the building. The display is a web page — published as a static site to
GitHub Pages and loaded on the TV by a thin Fire TV shell app.

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the architecture rationale and
[docs/BUILD_TREE.md](docs/BUILD_TREE.md) for the file tree and milestone plan.

**Status:** the scene engine, playlist, content schema and validator, local admin editor, and the
gallery and calendar adapters are all built, and the site is live on the television (M0 done).
`npm run publish` is the one supported way to publish (M2). The survival work is code complete
(M1): a Service Worker so the display boots offline, self-hosted fonts, a content version poll, a
stall watchdog, a `?diag=1` overlay, and event times pinned to an explicit time zone. **What is
left is proof** — none of it has run for a week on the actual television, which is M3.
**The Fire TV app under `app/` is active again** as a thin WebView appliance shell; the scene,
caching and refresh logic stays in `web/`. See [docs/BUILD_TREE.md](docs/BUILD_TREE.md) §5.

## Project layout

```
web/        The display itself — scene engine and playlist (HTML/CSS/JS), runs in any browser
content/    Editable VHF content: playlist, settings, artwork, announcements, generated event
            and photo data (source of truth on the PC)
sources/    PC-side adapters for external sources (gallery, calendar, Instagram)
scripts/    Build/publish/validation scripts
admin/      Local-only (127.0.0.1) content editor
dist/       Build output for the published site (git-ignored, generated by scripts/build-site.mjs)
tests/      Tests
docs/       Architecture and planning docs
app/        Android app (Kotlin) — thin Fire TV WebView shell, see docs/BUILD_TREE.md §5
```

## Preview locally

No Fire TV or Android tooling needed.

```bash
npm run preview
```

This validates every JSON file under `content/`, copies `web/` and the published subset of
`content/` into `dist/`, and serves `dist/` at `http://localhost:8080`. Add `?diag=1` for the
diagnostics overlay: uptime, content version, last sync, Service Worker state, cache hits, failed
images, error count and the current scene.

**Live site:** https://hambats.github.io/vhf-firetv-display (GitHub Pages, deployed by
[.github/workflows/deploy-pages.yml](.github/workflows/deploy-pages.yml) on every push to `main`).
`publishUrl` in [content/settings.json](content/settings.json) points at it, and the display polls
`<publishUrl>/content/version.json` to detect new content. A Netlify project (`vhf-firetv-display`)
still exists as a dormant fallback but isn't the active publish target — GitHub Pages replaced it
2026-09-18 after Netlify's free-tier deploy credits ran out mid-development.

## Refresh content from VHF sources

```bash
npm run sync-sources
```

Re-scrapes the VHF gallery and re-fetches the public VHF Google Calendar, rewriting
`content/generated/gallery.json` and `content/generated/events.json`. Inside Claude Code, the
`update-vhf-content` skill wraps sync → review → publish;
[docs/SCHEDULED_CONTENT_UPDATE.md](docs/SCHEDULED_CONTENT_UPDATE.md) is the same sequence written as
a standalone task for a recurring scheduled agent.

## Publish

```bash
npm run publish
```

The one supported way to update the display, and the single place the publish transport lives —
skills, the scheduled content task and the admin publish button all call it rather than repeating
the steps. It runs validate → build → test → commit → push → **verify**, and it is the last step
that matters: a push only *starts* a publish (GitHub Actions runs the deploy via
[.github/workflows/deploy-pages.yml](.github/workflows/deploy-pages.yml)), so the script polls
`<publishUrl>/content/version.json` until the published version actually advances, and fails if it
doesn't. A failed validate/build/test never pushes, so the previously published site stays live.

Useful flags: `--dry-run` (everything except commit and push), `--verify-only` (just read the live
version), `-m "message"`, `--timeout <seconds>`.

Only content the display actually fetches is published — see `PUBLISHED_CONTENT` in
[scripts/build-site.mjs](scripts/build-site.mjs). The curation files (`gallery-exclude.json`,
`events-exclude.json`) and anything under `content/artwork/candidates/` stay on the PC.

## Admin tool (local only)

```bash
npm run admin
```

A local-only server and page at `http://127.0.0.1:8787` for editing content instead of hand-editing
JSON: the playlist (add/reorder/edit/delete scenes), gallery pool weights (max photos, min
resolution, recency bias) with a button to re-run the sync, the gallery exclude list (browse the
current pool and exclude anything needing context an unattended TV can't provide), and
announcements — plus buttons to run the build and deploy.

Every save is validated the same way `build-site.mjs` validates before a deploy — a save that would
break `content/` is rejected and the previous file restored, so this can't produce a broken deploy.
It binds to `127.0.0.1` only and has no auth.

## Requirements

Node 18+ and npm. That's it for everyday work — content edits, preview, and deploys need nothing
else.

## Appendix: the Fire TV shell app

`app/` holds the Kotlin WebView shell, and **it is what the television runs** — v1.1.0 has been
installed since Sept 2026. (This appendix described it as dormant and never installed until
Sept 21, 2026; the status section above had been updated and this had not.)

It is deliberately thin: fullscreen, screen-on, immersive chrome, remote/back lockout, retry after a
network outage, and relaunch on boot. The scene engine, caching and content refresh all stay in
`web/`. A content change never needs a rebuild — only a change of publish endpoint does. See
[docs/BUILD_TREE.md](docs/BUILD_TREE.md) §5 and [docs/DISPLAY_SETUP.md](docs/DISPLAY_SETUP.md).

Building it needs Android Studio (or a standalone Android SDK) with SDK Platform 34, and a JDK 17+.
The gradle wrapper lives at the project root, not inside `app/`.

```bash
JAVA_HOME="/c/Program Files/Android/Android Studio/jbr" ./gradlew assembleDebug
```

The output APK is at `app/build/outputs/apk/debug/app-debug.apk`.

Installing does **not** require a PC-to-TV cable: the Downloader app from the Fire TV appstore works
(enable "Apps from Unknown Sources", type a URL, install), and since Sept 19 the television is on
Tailscale, so `adb -s 100.69.183.1:5555 install -r <apk>` works from anywhere —
see [docs/REMOTE_ACCESS.md](docs/REMOTE_ACCESS.md).
